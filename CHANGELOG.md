# Unreleased
- rule 27 (probable UDP protocol scan): a datagram counts as a probe only when its destination is a single host — not 255.255.255.255, not a multicast group (224.0.0.0/4) — and its payload does not start with the 6-byte Tailscale disco magic (54 53 F0 9F 92 AC), read from `udp.p_data`. One Tailscale path-discovery round or a LAN discovery broadcast has the rule's shape (one source, one target, many destination ports within 10 ms) and flooded it; every UDP scan trace of the review keeps its alerts. A scanner whose probes carry the disco magic or target a broadcast/multicast address is not counted — two declared evasions — and probes paced more than 10 ms apart were never counted, as before. A datagram bigger than the room in `input.max_message_size` (about 32.8 KB with the shipped `mmt-security.conf`, 3 KB without one) is not counted either, and mmt-security logs one "too big" warning per such packet; the field stack's `input.max-message-size = 131072` is unaffected. The separate UDP traceroute false positive is unchanged (luongnv89/security-rule-generator#55)
- packaging: `make install` and the deb and rpm packages no longer ship `rule_verif_engine_internal.h`; the header is for the engine only — `rule_verif_engine.c` and `mmt_single_security.c` include it, and no header that generated rule code includes reaches it (fork issue #56)
- engine: plugin ABI bump to 1.2.22 (`VERSION` and `REQUIRE_PLUGIN`): `rule_engine_t` leaves the plugin ABI. The generated guards read the message values through the new exported function `mmt_sec_rule_engine_get_msg_values()` instead of the `rule_engine_t.msg_values` offset, and `rule_verif_engine.h` (the header they include) keeps `rule_engine_t` opaque; the struct moves to `rule_verif_engine_internal.h`, for the engine only. A 1.2.21 rule `.so` is refused (rebuild it with this `compile_rule`); a 1.2.22 rule that calls the accessor (every shipped rule but one) fails at `dlopen` on an older engine (undefined symbol) instead of reading the wrong memory. `rule_abi.hash` now also covers the instance-key and fsm structs, `mmt_memory_t`, the enum values that rules compile in, and the accessor. The loader refuses a rule whose `version` pointer is NULL with a warning instead of dereferencing it, and no longer allocates 0 bytes when every rule of a plugin is refused (doc/rule-abi-stability.md) (fork issue #56)
- engine: plugin ABI bump to 1.2.21 (`VERSION` and `REQUIRE_PLUGIN`). The fork #51 instance index appends `instance_keys` to `rule_info_t` and moves `msg_values` in `rule_engine_t`, which the generated guards read: a rule `.so` must be rebuilt with this version's `compile_rule`. The loader refuses a rule older than `REQUIRE_PLUGIN` and, new, a rule built for a newer engine, with a warning, instead of crashing; `rule_info` applies the same check. An engine of version 1.2.20 or older cannot refuse 1.2.21 rules: do not install them with it (doc/rule-abi-stability.md) (fork issue #51)
- tools: `-h`/`--help` exits 0 for `mmt_sec_server` and `compile_rule` too (was exit 1 and exit 1 with no help); `mmt_sec_standalone` and `mmt_sec_server` accept `--help`. A bad option still exits 1, asserted for all four tools by `check-help` in `make check` (fork issue #47)
- packaging: a failed `make deb` removes its staging dir and `.shlibs-deps` file instead of leaving them (the leftover then broke the next `make deb` at `mv`); a stale staging dir is cleaned before staging, so `make deb`/`make rpm` are repeatable; the packages' commit part is `nogit` when the tree has no git metadata git can read, instead of empty (`make rpm` used to fail on an empty `Release:`); `check-build-info` checks `build.target` against a static allowlist of the triplets the generated macro chain can produce; readme.md: `dpkg-dev` is needed for `dpkg-shlibdeps` only (fork issue #47)
- packaging: the binaries no longer link `libmmt_tcpip.so` (nothing used it, and it broke `make` on RHEL/Rocky where gcc links `--no-as-needed`); the deb declares the shared libraries of its binaries via `dpkg-shlibdeps` (the libxml2 soname differs by release) and the real `Architecture:`; `make rpm`'s `mkdir -p` and spec writing work where `/bin/sh` is dash; `check-build-info` compares `build.target` to the triplet the compiler's predefined macros give, since `gcc -dumpmachine` can add a vendor part (Red Hat's `aarch64-redhat-linux` vs `aarch64-linux-gnu`) (fork issue #35)
- mmt_sec_standalone: new option `-R` enables IP defragmentation and TCP reassembly in MMT-DPI, so rules on `tcp.tcp_session_payload_up`/`tcp.tcp_session_payload_down` (e.g., rule 67, EICAR split over TCP segments) can fire. It is off by default: it costs memory (MMT-DPI keeps each TCP flow's payload), and a reassembled stream that does not fit in `input.max_message_size` is skipped, with one warning per run and a count at the end (see readme.md). Without `-R`, `-v` prints a hint when such a rule is loaded (Montimage/mmt-security#42)
- engine: rules testing a TCP flag attribute equal to 0 (e.g., `tcp.flags == 0`, rule 42 TCP NULL scan) now fire; zero-valued TCP flags were dropped (Montimage/mmt-security#28)
- compile_rule: stricter `delay_min`, `delay_max`, `counter_min` and `counter_max` values. A value must be a non-negative integer, with an optional leading `+`, optionally followed by one `+` or `-` that makes the bound strict (e.g., `5`, `+5`, `0+`, `6-`). Values such as `"0.5"`, `" 0"`, `"0++"` or `"1s"` were silently read as something else; a rule using them now fails to compile, with a message naming the attribute and its value. All rules shipped in rules/ compile as before. Third-party rules may need fixing (Montimage/mmt-security#52)
- compile_rule: no longer crashes (stack overflow) when it stops on an error in a rule file, and stops at the end of an unterminated string constant (Montimage/mmt-security#52)
- compile_rule: exits with a non-zero status when gcc fails to compile the generated code; it used to exit 0 (Montimage/mmt-security#52)
- CI builds and checks against MMT-DPI v1.10.3 (was 6b1c9f5, v1.7.10 plus 36 commits); v1.10.0 to v1.10.2 lose the TCP payload of reassembled IPv4 fragments, so `make check` 19.SQLI fails with them (Montimage/mmt-security#18)
- rules 230 and 231 (in rules/properties_all) for OCPP 1.6-J: Heartbeat flooding and SetChargingProfile limit above the site maximum; they need the OCPP 1.6-J protocol plugin of mmt-plugin-generator (doc/rule.md, section 7); their alerts carry ip.src, ip.dst, tcp.src_port and tcp.dest_port
- packaging: the deb (`make deb`) now depends on `mmt-dpi (>= 1.10.3)`, which it did not before, and the rpm (`make rpm`) requires `mmt-dpi >= 1.10.3` (was 1.6.9). The DICOM rules need MMT-DPI 1.9.0 or later, which bounds `tcp.payload_len` by the captured bytes; 1.10.3 is the release CI tests. The version is `MIN_DPI_VERSION` in the Makefile
- rules 206 (invalid DICOM data set type) and 212 (unexpected DICOM C-CANCEL) are disabled: they are moved out of rules/ and kept in rules/properties_all, because they alert on normal traffic. Any Command Data Set Type other than 0x0101 means a data set is present (PS3.7 E.1), so 206 alerted on every C-STORE and C-FIND request; C-CANCEL is a standard DIMSE operation, so 212 alerted on every cancelled query. They are no longer in the deb and rpm packages (fork issue #27)
